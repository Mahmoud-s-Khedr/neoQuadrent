# Findings from end-to-end testing

Bugs, limitations and surprises found while building the example projects. "neoquadrant" items are
in our code; "model" items are about the embedding models, not the database.

| # | Area | Finding | Status |
|---|------|---------|--------|
| 1 | neoquadrant (Node types) | `index.d.ts` exported an interface named `Record`, shadowing TypeScript's built-in `Record<K, V>`, so `Payload`, `CreateCollection` and `VectorInput` were broken types. It went unnoticed because `skipLibCheck` (on in most projects) skips `.d.ts` files. | **Fixed**: renamed to `PointRecord`. `npm run typecheck` in `bindings/node` and `examples/` now checks the declarations without `skipLibCheck`. |
| 2 | model | P1: on "how to reduce server response time", every small model tried ranks off-topic notes that share the query's words (support-ticket *response time*, restaurant *server*, *server* room) above the notes that answer it without sharing words (caching, profiling, DB indexes, N+1). Models tried: bge-small and bge-base, all-MiniLM-L6, e5-small, nomic-embed-v1.5, arctic-embed-m and the ms-marco MiniLM cross-encoder. The answers rank 8th to 33rd. mxbai-embed-large (335M) does better (profiling #4, mean rank 12.5 vs 16) but still lets one trap into its top 5. | Documented. P1 compares bge-small and mxbai-large as two named vectors in one collection. Overall, both still clearly beat BM25 (MRR 0.84 / 0.94 vs 0.54). |
| 3 | model | P3: in the workbook set, look-alike questions with different answers score almost exactly like true paraphrases: mean cosine 0.901 vs 0.910. Examples: "solid → gas" vs "gas → solid" at 0.991, and `2x + 6 = 14` vs `2x - 6 = 14` at 0.988. At the QQP-tuned threshold (0.82), 26 of 30 look-alikes are flagged as duplicates. | Mitigated in part with payload filters. A `numbers` multiset keyword filter removes 10 of 10 number look-alikes and keeps 26 of 28 paraphrases. The 16 wording look-alikes need answer-aware checking (an answer key or an LLM judge); no vector or filter can separate them. |
| 4 | neoquadrant: works | P3: the engine's cosine scores match locally computed dot products on all 5,000 QQP pairs (scored with `has_id`-filtered queries). `score_threshold`, `must_not` + `has_id`, and `facet` on keyword indexes all behave as documented. | No issue. |
| 5 | neoquadrant | P5: the same hybrid (RRF) query returned tied results in a different order on every call, and so differently after a reopen. Qdrant's `rrf_scoring` says it "does not break ties" and collects results in a hash map, and exact ties are common with RRF and with duplicate vectors. | **Fixed** in `Collection::query`: each run of equal (score, order_value) is ordered by point id. Only tied neighbours move. Conformance cases cover dense ties and RRF ties. A tie that straddles a prefetch `limit` is still decided inside the engine. |
| 6 | neoquadrant | P5: the query API only accepted `{"fusion": "rrf"}`. Qdrant's `{"rrf": {"k", "weights"}}` (weighted fusion) was missing. | **Added**, validated (one weight per prefetch, `k ≥ 1`) and typed in `index.d.ts`. Qdrant's weights *compress positions* (`1/((pos+1)/w + k − 1)`) rather than scaling scores, which my first test expectation got wrong; it's now pinned by a conformance case. |
| 7 | retrieval | P5: two planned hypotheses did not hold. (a) Semantic did not beat BM25 on "conceptual" queries (MRR 0.37 vs 0.53). The Node.js errors doc keeps dozens of error codes in one bulleted section, so 200-word windows mix them and dilute the dense vector (semantic misses EADDRINUSE and ECONNRESET entirely). My conceptual phrasings also share words with the docs ("too many open files"). (b) Plain RRF (0.72) lands *between* semantic (0.63) and BM25 (0.76), which is typical when one retriever is much weaker. | Reported, not asserted. BM25-weighted RRF reaches 0.78, but those weights were chosen after seeing the results. Structure-aware chunking (one chunk per error code or API entry) is the likely fix for (a). |
